# Evaluation

> Generated by `python -m sentinel_ml.render_eval` from `docs/data/evaluation_v1.json`. Every number below comes from that file, which comes from a real run (commit `fd3696d762`, model `dcb0100109c4`). Nothing is typed in by hand.

## What is (and is not) being measured

All attack and fault scenarios are **synthetic**: they are injected into a simulated spacecraft bus (driven by real PCoE battery and IMS bearing trajectories) and a real-data replay path. Training and test scenarios come from the **same simulator**, so these results measure how well the platform separates the simulator's scenario families, *not* accuracy on a real spacecraft. See [LIMITATIONS](LIMITATIONS.md).

- **Runs:** 462 (33 scenarios x 14 seeded variants; variants shift timing and scale magnitudes and change all noise). Each run is 1,800 simulated minutes.
- **Splits (by variant index):** train [0, 1, 2, 3, 4, 5, 6, 7], validation [8, 9], test [10, 11, 12, 13]. Every scenario appears in every split with different seeds. Incident windows: train 357, validation 90, test 199.
- **Model:** multinomial logistic regression (C=0.3, temperature 1.04); abstention thresholds tau=0.30, delta=0.45, tuned on validation only to reach >= 90% answered accuracy at maximum coverage. The test split was scored once, after all design iteration on validation.
- **Real inputs used:** pcoe trajectories; space weather from real DONKI data (context per run: {'quiet-verified': 448, 'aligned': 14}).
- **Caveat on the intervals:** windows from the same scenario are not independent (4 test seeds per scenario), so the 95% Wilson intervals are optimistic. Treat differences of a few points as noise.

## False alarms

On 12 nominal test runs (15.0 simulated days) the detectors opened **10 incident windows (0.67 per simulated day)**. Attribution labeled 40.0% (4/10; 95% CI 17-69%) of them `nominal`; 6 would reach an operator. A further 46 windows opened outside the injected fault in fault runs (including ones caused by the fault's aftermath).

## Generalization to unseen scenario types (leave-one-scenario-out)

Training on every scenario **except** one, then classifying the held-out one: 16 of 30 scenarios are still classified correctly at >= 75%, and 10 are never classified correctly (`bearing_wear`, `manip_bias_load`, `manip_lowslow_battv`, `manip_ramp_battv`, `sensor_drift_battv`, `sensor_dropout_battt`, `sensor_noise_vib`, `seu_sep_aligned`, `spoof_battv_clean`, `spoof_vib_hide`). The learned model recognizes *families it has seen*; it does not reason its way to a new failure mode. The ones that do generalize: `auth_bruteforce`, `auth_new_source`, `auth_offwindow`, `cmd_out_of_window`, `cmd_unauthenticated`, `cmd_unauthorized`, `cmd_unknown_source`, `cmd_whitelisted_anomalous`, `comms_jamming`, `comms_rogue_uplink`, `dos_dropout`, `dos_flood`, `dos_malformed`, `replay_append`, `replay_replace`, `sensor_stuck_battv`.

These are mainly the slow, in-limits, single-sensor cases (`manip_*`, `spoof_*`, `sensor_drift_battv`) and slow degradation. Their evidence is one sensor departing gradually from another, and the platform's features cannot tell an attacker's clean synthetic values, a drifting sensor and a low-and-slow manipulation apart. **The correct behavior is to say so**: most such windows end as `needs_human` rather than a confident wrong class. That is a limitation of the evidence, not a solved problem.

## Reproduce

```bash
python scripts/tasks.py data                 # real datasets (DONKI needs a cached window)
uv run python -m sentinel_ml.make_dataset    # 462 scenario runs -> data/processed/records.pkl (~7 min)
uv run python -m sentinel_ml.evaluate --out ml/runs/attribution-v1
uv run python -m sentinel_ml.render_eval --metrics ml/runs/attribution-v1/metrics.json
```
