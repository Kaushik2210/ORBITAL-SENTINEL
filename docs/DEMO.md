# Demo script (~3 minutes)

Every step below is something that was actually run against the real, working platform — this is
not aspirational. `frontend/e2e/mission-control.spec.ts` automates the same path end to end
(sign-in → launch → incident → agent report → reveal) against a real backend on every CI run.

## Setup (~2 minutes, once)

Fastest: open the live deployment, <https://web-production-ddd02.up.railway.app> — read-only browsing
(steps 1 and the first half of 3) needs no account; ask whoever's presenting for sign-in credentials to
launch a scenario, or run the platform yourself:

```bash
cp .env.example .env   # fill in JWT_SECRET, POSTGRES_PASSWORD, ADMIN_EMAIL, ADMIN_PASSWORD
docker compose up --build
```

Open <http://localhost:3000>. (No Docker? `python scripts/tasks.py serve` +
`cd frontend && npm run dev` works the same way — see the root README's "Try it".)

## 1. Sign in (10 s)

`/login` with the account from `ADMIN_EMAIL`/`ADMIN_PASSWORD`. Without signing in at all, `/` and
`/incidents` are still browsable — `PUBLIC_DEMO_MODE=true` gives anonymous visitors read-only
access; starting a session or running the agent needs the account.

## 2. Launch an attack (20 s)

`/scenarios` — 33 scenarios: 7 attack families, sensor faults, real battery/bearing degradation
trajectories. Pick **"Password guessing"** (`auth_bruteforce`) and hit **launch**. This lands on
`/sessions/{id}`, streaming live over a WebSocket.

## 3. Watch it happen (~10 s at unpaced speed)

The telemetry chart updates live (uPlot); the progress bar fills; **"Incidents raised in this
session"** goes from 0 to 1 partway through, well before the run finishes — the platform doesn't
wait for a session to end to raise an incident.

## 4. Open the incident (15 s)

Click through. This is the interesting part:

- **Posterior** over five classes plus `needs_human` — for this scenario, `cyberattack` at ~99%.
- **Evidence** — the *exact* signed contributions behind that number (`auth_anomaly`,
  `l3_sidedness`, …), not a black box. `+`/`−` for and against.
- **Detector outputs** — every one of the ~80 raw detector firings behind the incident window,
  each with its own one-sentence explanation.

## 5. Ask the AI agent (10 s)

Click **investigate**. Without `ANTHROPIC_API_KEY` set, this is the deterministic offline
fallback — say so out loud, it's the honest default and the only agent path verified end-to-end.
The report still cites the real evidence, gives a recommended action, and states its own caveat
(*"generated by the deterministic offline fallback…"*). With a key configured, the same button
runs a real Claude tool-use loop over eight read-only evidence tools instead.

## 6. Reveal ground truth (10 s)

Back on the session page, once it's finished: **"What actually happened is hidden until you
ask"** — click **reveal**. This is the point of the whole platform: compare what the detectors and
the attribution model concluded (step 4) against what was actually injected. For this scenario
they match; for the "hard" scenarios (marked in the library) — slow single-sensor drift — the
platform correctly answers `needs_human` instead of guessing, and that's the honest headline
finding of the whole project, not a bug to hide. See [`docs/LIMITATIONS.md`](LIMITATIONS.md).

## If asked "what's not real here"

Be direct: every **attack** is synthetic, run by this project's own simulator — say so before
anyone asks. What's real: the NASA SMAP/MSL telemetry-anomaly dataset, PCoE battery and IMS bearing
degradation trajectories driving the synthetic fault scenarios, and NASA DONKI space-weather
events. None of it is redistributed; `make data` downloads it fresh, checksummed.
[`docs/DATASETS.md`](DATASETS.md) has the full provenance and every surprise found along the way.

## If there's more time

- `docs/EVALUATION.md` — the real numbers (86.4% forced-choice attribution accuracy, the ablation,
  the confusable-pair table, the honest real-SMAP/MSL detection results).
- `docs/THREAT_MODEL.md` — the STRIDE analysis, including the AI agent's specific prompt-injection
  surface and why the read-only tool boundary (not prompt wording) is what actually defends it.
- `GET /audit/verify` — the hash-chained audit log; tamper with a row directly in the DB and watch
  it report the exact row that broke.
